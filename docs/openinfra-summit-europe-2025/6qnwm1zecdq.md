# Summary

Cloud Federal presented a solution to a critical resource management issue in OpenStack where multi-NUMA installations suffered from unintended memory overcommitment, leading to VM crashes.
The root cause was identified as the Placement service’s inability to distinguish between NUMA-aware and unaware nodes, resulting in a lack of per-NUMA resource tracking and safe candidate generation.
To address this, the team implemented a configuration that splits compute resources into separate NUMA-specific resource providers within Placement, ensuring that memory and CPU allocations are strictly tracked per node to prevent overcommitment.
The presentation also detailed significant performance challenges encountered during deployment, specifically the exponential growth of invalid allocation candidates generated by the "same subtree" filtering process, which was mitigated by modifying Placement code to understand NUMA topology structures.
Additionally, the speakers discussed the necessity of using huge pages for accurate per-NUMA memory tracking and outlined the migration steps required to resolve existing overcommitments before enabling the new safeguards.

|   1 | The Cloud Federal, a European cloud provider, identified a resource management issue in OpenStack where multi-NUMA installations caused VM crashes due to unintended memory overcommitment.                                 |
|   2 | Non-Uniform Memory Access (NUMA) efficiency is critical in modern dual-socket servers, as accessing remote memory significantly reduces performance compared to local memory access.                                        |
|   3 | The OpenStack scheduling process involves Nova Compute, Placement, and the Scheduler, with Placement responsible for storing inventories and providing safe allocation candidates.                                          |
|   4 | The root cause of the crashes was that Placement did not distinguish between NUMA nodes, treating the entire compute node as a single resource provider, which allowed overcommitment of specific NUMA nodes.               |
|   5 | The proposed solution splits the compute node into multiple resource providers in Placement, one for each NUMA node, to enable accurate tracking of CPU and memory per node.                                                |
|   6 | This approach aligns with a previously accepted but unimplemented community spec called "NUMA topology with resource providers."                                                                                            |
|   7 | A new configuration option, `enable_numa_reporting_to_placement`, allows administrators to enable or disable this behavior, with `true` enforcing NUMA-aware scheduling and preventing overcommitment.                      |
|   8 | Existing options like `reserved_hugepages` should be used instead of `reserved_host_memory_mb` to reserve memory on specific NUMA nodes when the new feature is enabled.                                                    |
|   9 | Performance issues arose because Placement generated a massive number of invalid allocation candidates, particularly for large flavors, leading to high resource usage and potential crashes.                               |
|  10 | The team optimized candidate generation by modifying Placement code to understand NUMA tree structures, reducing the number of invalid candidates generated from billions to thousands.                                     |
|  11 | A secondary performance issue involved the lack of a robust isolation policy in Placement to ensure different request groups are satisfied by different providers, resulting in duplicate invalid candidates.               |
|  12 | The migration process required manual steps to fix existing overcommitments, including pinning OS services to NUMA node zero, reserving memory, and migrating affected VMs before enabling the new feature.                 |
|  13 | The solution prevents new overcommitments but does not automatically fix existing ones, requiring careful planning and verification of resource states before deployment.                                                   |
|  14 | The team plans to upstream these changes to the OpenStack community, noting that the feature has been pending for years and is essential for safe NUMA-aware scheduling.                                                    |
|  15 | Questions from the audience highlighted concerns about live migration across different topologies and the importance of setting `hw:mem_page_size` to avoid pinning VMs to NUMA nodes without checking memory availability. |
|  16 | The team confirmed they are testing on stable OpenStack versions and are working on further optimizations to address scalability and performance challenges in large-scale deployments.                                     |
