# Summary

Douwe Osinga, head of the Goose agent at AAIF, argues that the traditional agent loop should be replaced with an agentic state machine to improve reliability, testability, and code readability.
The core thesis is that modern agents rely on a simple loop that becomes increasingly messy as features like approvals, compaction, and MCP elicitation are added, leading to scattered state management and difficult debugging.
By treating the conversation as the explicit state and breaking the agent into discrete, independent operations, the system becomes resumable, allowing it to persist to disk, restart after crashes, and handle long-running tasks without blocking servers.
This architecture also enhances testability by enabling developers to replace specific components with fakes and facilitates experimentation by allowing new features to be added as isolated operations that can be easily toggled or removed without polluting the core logic.
Ultimately, this approach results in cleaner, more organized code where each operation is self-contained, making it easier to manage complex agent behaviors and integrate community-driven experiments.

# Main Points

|   # | Main point                                                                                                                                                                                                                                                                                          |
| --: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|   1 | : Modern AI agents typically rely on a simple loop structure, which should be replaced by an agentic state machine to improve robustness and maintainability.                                                                                                                                       |
|   2 | : State machines allow agents to persist state to disk after each step, enabling the agent to stop, restart, or resume from any point without losing context, which is critical for server-side applications and crash recovery.                                                                    |
|   3 | : By decoupling components into separate operations, individual parts can be tested in isolation. Side-effecting components (like real-world tool calls) can be replaced with fakes to test other components in parallel.                                                                           |
|   4 | : The state machine architecture allows for easy A/B testing or feature experimentation. New functionalities can be added as independent operations that can be toggled on or off without polluting the core agent loop.                                                                            |
|   5 | : The approach results in cleaner code where each operation is encapsulated in a single file. This is particularly important in an era where much code is generated by AI agents, as it prevents the accumulation of messy, interdependent logic.                                                   |
|   6 | : Classic agent loops become messy as concerns like approvals, MCP elicitation, and context compaction are added. These features require complex state tracking and conditional checks within the loop, leading to bugs and difficult maintenance.                                                  |
|   7 | : In the state machine model, the conversation itself acts as the shared state. Each operation reads the conversation, performs a specific step, and returns explicit changes (effects) or yields control, rather than relying on loose variables within a loop.                                    |
|   8 | : Specific behaviors are owned by dedicated operations. For example, a "recipe" operation owns its specific tools and prompts, ensuring they are only active when needed. This prevents issues where tools are incorrectly injected or missed during resumption.                                    |
|   9 | : Approvals are handled by yielding control back to the client. The client detects unapproved tool requests in the conversation state, prompts the user, and restarts the agent. This ensures that refreshing the client window does not lose the approval state.                                   |
|  10 | : The system distinguishes between durable "facts" (changes to the conversation state that are persisted) and transient "events" (real-time updates streamed to the user, such as progress indicators). This separation prevents state inconsistencies between the in-memory loop and disk storage. |
|  11 | : The state machine supports event-driven waking. Agents can remain dormant until specific triggers occur (e.g., new email, camera detection), avoiding the token waste of continuous polling or heartbeat checks.                                                                                  |
|  12 | : The same state machine used in production can be used for testing by replacing external dependencies (like HTTP) with scriptable engines, allowing for the reproduction of real-world failure scenarios.                                                                                          |
|  13 | : If a process is killed while a tool call is executing, the system does not automatically record the success of that call. However, it is better than the old model because the agent can query the LLM to decide whether to retry the action based on its nature (idempotent vs. destructive).    |
|  14 | : The order of operations is currently defined manually. While the system works cooperatively, there is no automatic dependency resolution to determine the optimal order of steps, which remains an area for future improvement.                                                                   |
